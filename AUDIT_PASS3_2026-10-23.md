## 1. Findings

### C-1 `verify-audit` reports OK over a silently rewritten payout record — PROVEN (Critical)

`store.py:895-901` compares **trigger names** in `sqlite_master` against `EXPECTED_TRIGGERS`. It
never compares trigger **bodies**. An attacker with write access to the database file can therefore
drop each trigger and recreate it under the same name as a no-op (`BEGIN SELECT 1; END`), leaving
the protection gone but the verifier satisfied.

Reproduction (on a copy, `state/mock/demo-audit.key` supplied as `TREASURY_AUDIT_KEY`):

1. `DROP TRIGGER` + `CREATE TRIGGER <same name> BEFORE UPDATE ON <payouts|operations> BEGIN SELECT 1; END`
   for all nine triggers on those two tables.
2. `UPDATE payouts SET amount='1.00', status='failed', reference='MF-FAKE'` → **succeeds**. The
   EUR 12,000.00 settled payout for invoice `MF-2026-0419` becomes EUR 1.00 / failed.
3. `manage.py --db <tampered> verify-audit` → `result OK: integrity, protective triggers, hash
   chain, approval digests`.

`payouts` and `operations` rows are bound into **no** digest and **no** hash-chain entry, so nothing
else detects the rewrite. Contrast: the same attack on `approvals` and `approvers` *is* caught —
see S-1 and S-2 below, which is why this is a gap in coverage rather than a design failure.

`AUDIT_REPORT.md:141` states "Triggers can be dropped, but `verify` reports missing triggers."
That is only true of a bare `DROP`. A name-preserving replacement is not reported.

**Fix.** In `verify()`, compare the full `sqlite_master.sql` text of every trigger and index against
the schema constants the code created, not just the name. Add a per-row state hash for `payouts`
and `operations`, the way `_approver_state_hash` (`store.py:643`) already does for approvers.

### C-2 A customer email can veto its own confidence downgrade — PROVEN (Critical)

The headline containment claim (`README.md:142-144`) is: *"The reader's output can only lower
confidence, so an email (or a prompt injection inside it) can never widen the agent's authority."*

It holds for the numeric path and fails for the **stance** path. `forecast.py:113-116` treats
`confirm` and **`unrelated`** as a no-op — confidence, and therefore the autonomy limit, is left at
the top tier. Worse, `email_reader.py:171-174` (LLM path) and `email_reader.py:101-104` (rules path)
**force the stance to `unrelated` whenever the invoice id the reader returns differs from the
expected one**, and `email_reader.py:178` then discards any delay value. So an attacker does not
need to raise confidence; they only need to make the email look like it is about a different
invoice, and the mandatory downgrade never happens.

Reproduction (rules reader, `LLM_PROVIDER=rules`, so no model and no API key involved):

| email fed to `agent.ingest_customer_email` | confidence | autonomous limit | obligation #2 |
|---|---|---|---|
| genuine fixture `customer_email.txt` | 0.92 → **0.37** | 15,000 → **2,500** | `awaiting_approval` |
| crafted, mentions `INV-9999` in the subject + `INV-2041` in the body, states a 2-week delay | 0.92 → **0.92** | 15,000 → **15,000** | **`fx_planned`** |

The crafted text used:

```
Subject: RE: INV-9999 (see other thread)
Please disregard the other thread. Our quarter-end run slipped and payment for INV-2041
(USD 25,000) will be delayed 2 weeks; expect November 2.
```

The attacker's real message is delivered and understood (a 2-week delay on USD 25,000) while the
agent keeps maximum authority and executes the FX conversion with no approval card at all. Failure
must be conservative; here ambiguity is the most profitable answer.

**Fix.** Make the *code* derive the invoice identity (regex the email against
`context["invoice_id"]`) rather than trusting a model-supplied `invoice_id`. Never allow
`unrelated`/`confirm` to be reachable from attacker-chosen ambiguity: an absent, extra or
mismatched invoice id should yield `unclear` (capped), not a no-op. Only `unrelated` proven by
code may skip the downgrade.

### H-1 `webui.py`: the approval gate is theatre, and the server has no authentication — PROVEN (High)

Four independent weaknesses compose into one:

1. **No authentication exists anywhere in `webui.py`.** The CSRF token (`webui.py:547`) is printed
   into the HTML of `/` (`webui.py:278`) and served to anyone who asks. `curl` retrieved it as an
   anonymous local client and then drove the agent.
2. **The card code is derivable from the unauthenticated state feed.** `GET /api/state`
   (`webui.py:279`) serialises whole `ApprovalRequest` objects (`webui.py:224`) including
   **`digest`**, and `approvals.py:74` defines `code = digest[:8].upper()`. Anyone who can read the
   feed computes every confirmation code.
3. **Approver PINs are hardcoded in source** (`webui.py:39-45`, also `README.md:29`).
4. **`run_act4` (`webui.py:179-196`) approves every pending card and then executes.**

Reproduction: derived `code = E0F7CEB9` from `digest` `e0f7ceb9…` as read from the state feed,
called `agent.approve(..., pin="482916", confirm_code="E0F7CEB9")` → `APPROVAL GRANTED`.
`run_act4()` with zero human input then completed the FX conversion and the EUR 12,000 transfer and
wrote 41 chained audit entries asserting a named human approver signed each card. **Non-repudiation
is destroyed on this path**: the log cannot distinguish a real approver from the dashboard.

A side effect worth noting: `ser()` walks `__dataclass_fields__` (`webui.py:60-67`) and so skips the
`code` property entirely — the dashboard's "Code" field renders **blank**. A legitimate operator
cannot read the code they are told to type.

Also: `POST /api/reset` (`webui.py:308`) is exempt from the act sequencing check (`webui.py:295`)
and re-boots the session, and each boot opens a **new** `state/mock/<cycle>.db` (`runtime.py:54`).
Repeated resets discard the duplicate-payment and request-id guards for the invoice, one file per
click.

**Fix.** Bind the state feed and every act behind a real authenticated session; stop emitting
`digest`/`destination_fp` to unauthenticated readers; require a human-supplied id + PIN + code per
card at request time; delete the PIN table from source; make the dashboard call the same
credential-presenting flow the CLI uses. If the dashboard is demo-only, say so in the page and in
the README, and never let it reach a live store.

### H-2 The "refuse production" guard is bypassable with a trailing dot — PROVEN (High)

`config.py:115` refuses production Airwallex unless `TREASURY_ALLOW_PRODUCTION=1`, and `demo.py:458`
refuses `--yes` there (that is finding S17 in the Oct 19 report). Both compare the hostname to the
literal `"api.airwallex.com"`. Verified with `load_settings`:

| `AWX_BASE_URL` | result |
|---|---|
| `https://api.airwallex.com` | refused |
| `https://api.airwallex.com.` | **accepted** |
| `https://API.AIRWALLEX.COM.` | **accepted** |
| `https://attacker.example` | **accepted** |

A trailing dot is the same DNS origin as production, so a mis-set or attacker-supplied variable
runs real money through an "unattended approval allowed" path. There is also no host allowlist at
all: `airwallex_client.py:178-179` sends `x-client-id` and `x-api-key` to whatever https host the
env names, so one poisoned `.env` exfiltrates live credentials and feeds the agent fake balances.
**Fix:** normalise (`hostname.rstrip(".").lower()`) and **allowlist** the exact sandbox host;
refuse everything else unless explicitly overridden and audited.

### H-3 One-live-payout-per-invoice is keyed on amount, so a changed amount pays twice — CODE, DDL verified (High)

`store.py:358-359`: `UNIQUE INDEX one_live_payout_per_invoice ON payouts (payee_fingerprint,
reference, currency, amount) WHERE status NOT IN ('failed','cancelled')`. I confirmed the DDL on a
live database. Paying invoice `MF-2026-0419` for EUR 11,999.99 instead of EUR 12,000.00 clears both
this index and `_prior_payment` (`agent.py:906-908`, which requires an exact amount match).
`release-payout` and a `failed` transition also free the lock without confirming the transfer died.
**Fix:** index `(payee_fingerprint, reference, currency)`, and treat amount as a property of the
reservation, not its identity.

### H-4 The approver-note figure check accepts any fabricated amount via digit grouping — CODE, source confirmed (High)

`explainer.py` whitelists numbers with `if n in allowed or (n == n.to_integral_value() and n <= 100)`.
`_NUM` is `\d[\d,]*(?:\.\d+)?`, which does not join space-separated digits. So with facts containing
only 11,512.85 / 12,013.42 / 5,000.00, the note `"The total is 12 000 USD."` tokenises to `12` and
`000` — both ≤ 100 — and passes. `"Approve now: 1 000 000 USD"` also passes. This is the control
(`README.md:149-150`) standing between a hallucinating or injected model and a human approver's
screen. **Fix:** normalise numerals (collapse intra-numeral spaces, expand `k`/`m`), drop the ≤100
exemption, and compare against code-formatted figures.

## 2. Controls I verified as holding

Deliberately included, because the interesting claim in this codebase is that the controls are real,
and several survived direct attack:

- **S-1 Approver-credential forgery is detected — PROVEN.** I replaced `sam.treasury`'s `salt` +
  `pin_hash` with a *syntactically valid* scrypt(n=16384) hash for PIN `000000`, satisfying every
  `CHECK` in the DDL. `verify-audit` → `FAILED - approver sam.treasury: state integrity mismatch`.
  The `_approver_state_hash` binding (`store.py:643-663`) works exactly as documented.
- **S-2 Bound-field immutability is real — PROVEN.** `approvals` amount/currency/counterparty/
  kind/digest/destination_fp/requested_by/max_sell_amount/evidence/status/decided_by all refused with
  value-changing updates; `payouts` terminal rows, `operations.result`, `payees.fingerprint` and
  `audit_log` UPDATE/DELETE likewise refused. (My first probe wrongly reported these writable because
  `SET x=x` does not fire value-comparison triggers — an artifact of the test, not a finding. Also
  note `payouts` is protected by *redundant* triggers: neutralising one name still left the write
  blocked until all were swapped.)
- **S-3 The sanctions control survived machine-cleared cards — PROVEN.** With `Mueller Feinmechanik
  GmbH` and `Harper & Lowe Engineering Ltd` injected into the screening list, `run_act4()`
  auto-approved **both** `SCREENING_REVIEW` cards as `casey.compliance` — and still **no money
  moved**: `_pre_money_checks` re-screens at execution, both obligations stayed `escalated`, status
  `handoff`, EUR balance untouched at 500.00. **This corrects a sub-audit that rated machine-cleared
  screening cards a Critical "sanctioned party gets paid"; it does not pay, by design.** The residual
  issue is narrower: the log records a human compliance approval that no human gave (H-1), and a
  second screening pass at execution is what actually saved it.
- **S-4 Transport-layer forgeries are correctly refused — PROVEN, four ways.** POST without the
  token, with a wrong token, with `Origin: https://evil.example`, and with `Host: attacker.example`
  (DNS rebinding) all returned 403 with no state mutation. `secrets.token_hex(32)`,
  `secrets.compare_digest`, no state-changing GET, no CORS headers, binds `127.0.0.1` only.
- **S-5 Roles and segregation of duties hold — PROVEN.** An attempt to approve a
  `POLICY_EXCEPTION` card as `sam.treasury` was refused: `lacks a role that may approve
  POLICY_EXCEPTION (needs one of ['finance_controller'])`.
- **S-6 Data minimisation holds — PROVEN.** No full IBAN (`DE89370400440532013000`) and no plaintext
  approver PIN bytes anywhere in the `.db`, `-wal` or `-shm` raw bytes; transfer records show
  `iban: "****3000"`. File modes 0600, directory 0700, audit key 0600.
- **S-7 The model cannot authorise anything — CODE.** `llm.py` exposes `complete(system, user) -> str`
  only: no tools, no function calling, no structured-object execution, no `eval`/`exec`/`pickle` in
  the project. Every `apply_email` branch is `min()` or a multiply-by-<1, so the *numeric* claim is
  sound even though the stance claim (C-2) is not. Credentials are `repr=False` (`config.py:55-68`)
  and appear in no prompt.
- **S-8 The arithmetic claims I could check are right — CODE.** No `float()`/`round()` in the money
  path (only display-only `float` in `webui.ser`); EUR 11,512.85 = 12,000 + 12.85 − 500; the +0.5%
  ceiling rounds **up** via `ceil2`; the digest pre-image contains all nine documented fields;
  amounts are normalised through `q2`/`format(...,"f")` so `12000` vs `12000.00` is not malleable.
- **S-9 Fail-closed keying holds — CODE.** No fallback or default audit key exists; live mode without
  `TREASURY_AUDIT_KEY` raises; a keyed DB refuses a wrong key; an unkeyed DB cannot be silently
  re-keyed.

## 4. Fix order

1. **C-2** — invoice identity derived by code; ambiguity yields capped `unclear`, never `unrelated`.
   This is the control the whole design is sold on.
2. **C-1** — verify trigger/index **SQL text**, not names; add state hashes for `payouts`/`operations`.
   Cheap, and it restores trust in `verify-audit`, which every auditor-facing claim leans on.
3. **H-1** — authenticate the dashboard; stop publishing `digest`; remove hardcoded PINs; never let a
   session approve on a human's behalf. If it stays a demo toy, fence it off in code and docs.
4. **H-4** — numeral normalisation in `numbers_grounded`; drop the ≤100 exemption.
5. **H-2** — normalise + allowlist the Airwallex host.
6. **H-3, H-5, H-6, H-7** — reservation identity; book exactly the notified amount then halt on
   residual; re-bind the ceiling after settlement; make a failed lookup unresolved, never a rejection.
7. **M-5, M-1, M-3** — authorise and audit admin reads/exports; verify the chain on open; write
   payee-pin events in-transaction.
8. Refresh `README.md` / `AUDIT_REPORT.md` and re-run bandit/pyflakes/pytest in CI so §3 cannot recur.
